## The problem

Boomi stores every integration as XML behind a graphical editor, and that is hard ground for an AI agent.
Leave out certain attributes and the editor breaks.
Invent one and the platform silently replaces it.
Invent a reference and the whole component fails late, after the work looks finished.
An LLM typing that XML directly produces work nobody can easily trust.

## What I built

Fathom lets an agent work inside Boomi the way it works inside an ordinary software project, with source files, a compiler and tests.

- **A spec instead of XML.** The agent describes an integration in a short YAML file that follows a published schema, and never edits Boomi's XML directly.
- **A compiler that catches mistakes.** It turns the spec into Boomi's XML, covers all 25 kinds of process step, and rejects mistakes before anything reaches Boomi. Embedded Groovy and JavaScript are checked too.
- **A preview before every change.** The agent shows exactly what will change in the account before it pushes, and a push either completes or rolls back.
- **A person at every step that cannot be undone.** Reading, compiling and previewing run freely. Deploying or running anything on a live system waits for a person to confirm it.
- **Tests tied to the version tested.** Processes are tested with fixtures on the platform, and a deploy is refused for a process without a test.
- **The team's own rules.** A handbook in a shared repository holds the team's naming, folder and design conventions, and every check follows it.
- **Design before build.** An interview settles every design question into a written design record before any spec exists, and a local preview draws the result in Boomi's own forms.

<h2 id="plugin">Built as a plugin</h2>

Fathom shapes what the agent knows, what it may do and when it must stop, through the parts an agent plugin is made of.

- **Thirteen skills** carry the knowledge: Boomi's concepts and component formats, the team's handbook, the design interview, testing, promotion between environments, and bringing changes made in Boomi's editor back into the spec.
- **Hooks** act on every move the agent makes. A gate reads each shell command and file write before it runs and holds anything that would change a live system until a person confirms it. Each spec is validated the moment the agent saves it, and each session opens with the Boomi account and handbook the agent is working with.
- **A review subagent** reads a finished spec against its design record on its own and reports every mismatch, without editing anything.
- **A language server and an MCP server** give editors live diagnostics and connect agent hosts that have no shell.
- **One plugin, two hosts.** The same skills and toolchain run in Claude Code and GitHub Copilot CLI, with an adapter for each host's hooks and permissions.

## How it was built

I designed Fathom and made its decisions, and an LLM wrote much of the code inside the same rules Fathom enforces.
The toolchain is one Go binary with about 380 test files, released by a pipeline for Linux, macOS and Windows, with a Rust port under way.
It reached a working toolchain in weeks of development, not months.

## Where it stands

Fathom is at version 0.58, proven in sandboxes and in read-only work on a large client account.
