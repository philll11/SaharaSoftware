## The problem

Ask an AI agent the same thing twice and you can get two different answers.
In an ordinary codebase that is manageable, because a compiler and tests catch the difference.
Boomi gives an agent almost nothing to check against.
Integrations are XML behind a graphical editor: leave out an attribute and the editor breaks, invent one and the platform silently replaces it, invent a reference and the whole component fails late, after the work looks finished.
Every gap is a place where the agent has to assume, and assumptions are where mistakes happen and tokens are wasted.

## The core idea: make Boomi deterministic for the agent

The most important decision in building any AI tool or plugin is to make the agent's world as deterministic as possible, so there is little room left for assumption.
Fathom does that for Boomi: it opens the platform up so an agent understands it the way it understands an ordinary software project.

- **A spec instead of XML.** The agent describes an integration in a short YAML file that follows a published schema.
- **A deterministic compiler.** The same spec always compiles to the same Boomi XML, across all 25 kinds of process step, and anything wrong is rejected before it reaches Boomi.
- **The account as facts.** Existing processes decompile into the same typed specs, and an index of the account tells the agent what already exists, so it reuses components rather than guessing at them.
- **The team's rules, written down.** A handbook holds the account's naming, folder and design conventions, and the checks apply them mechanically.
- **The toolchain draws, never the model.** Pictures, layouts and generated components come from the toolchain, so they come out the same every time.
- **A preview before every change.** The agent shows exactly what will change in the account before it pushes, and a person confirms anything that touches a live system.
- **Tests tied to the version tested.** Processes are tested with fixtures on the platform, and a deploy is refused for a process without a test.

## The design stage

Most of an agent's costly mistakes start in the design: a requirement it assumed, a convention it did not know, a shape the developer pictured differently.
Corrections after a build cost the most, because by then the agent has guessed and spent the tokens.
Fathom's design stage puts the developer and the agent on the same picture before anything is built.

- **An interview first.** The agent asks the design questions that matter and writes the answers into a design record, so requirements are settled rather than assumed.
- **A visual preview in Boomi's own forms.** A local page draws the integration's landscape, every process on its canvas as Boomi's editor shows it, every map and the components in the folders they go to. It follows the files as the agent writes them.
- **The developer shapes it.** On the landscape the developer adds and connects processes, queues and systems, or reuses ones the account already has. The processes are generated from that picture, and the developer then refines labels, names and folders and places the components. Each of these is a deterministic edit to the spec, with no agent in the loop.
- **A conversation on the page.** The developer pins a remark to anything the page draws, the agent asks its questions on the element they concern, and one button hands everything back to the session.

In effect, the developer builds the Boomi flow without having to build it in Boomi first.
They stay engaged in the design instead of reviewing a finished build, and the agent has far less to assume.
What the preview draws is what Boomi's editor shows after the push: one layout feeds both, and a test holds them equal.

<h2 id="plugin">Built as a plugin</h2>

Fathom shapes what the agent knows, what it may do and when it must stop, through the parts an agent plugin is made of, each designed to leave the agent as little as possible to assume.

- **Thirteen skills** carry the knowledge: Boomi's concepts and component formats, the team's handbook, the design interview, testing, promotion between environments, and bringing changes made in Boomi's editor back into the spec.
- **Hooks** act on every move the agent makes. A gate reads each shell command and file write before it runs and holds anything that would change a live system until a person confirms it. Each spec is validated the moment the agent saves it, and each session opens with the Boomi account and handbook the agent is working with.
- **A review subagent** reads a finished spec against its design record on its own and reports every mismatch, without editing anything.
- **Output written for agents.** Every command keeps its output short and puts the next step first, so a session never misses what a step needs.
- **A language server and an MCP server** give editors live diagnostics and connect agent hosts that have no shell.
- **One plugin, two hosts.** The same skills and toolchain run in Claude Code and GitHub Copilot CLI, with an adapter for each host's hooks and permissions.

## How it was built

I designed Fathom and made its decisions, and an LLM wrote much of the code inside the same rules Fathom enforces.
The toolchain is one Go binary with about 380 test files, released by a pipeline for Linux, macOS and Windows, with a Rust port under way.
It reached a working toolchain in weeks of development, not months.

## Where it stands

Fathom is at version 1.0 and live.
Developers on the integration team at a large European construction company use it for their integration work, in Claude Code and GitHub Copilot CLI.

## What this means for you

The principle behind Fathom applies to any AI tool or plugin: make the agent's world as deterministic as possible, and bring people into the design where judgement is needed.
